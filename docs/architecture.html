Structure

The shape of it

The entire prototype is one file — preview/app.html, 7,874 lines, 491 KB. No bundler, no framework, no npm install to see it run. Open it from disk and it works, offline, in any browser.

That is a deliberate constraint, not a shortcut. A prototype whose job is to be reviewed daily by people who do not run a dev server has to open from a double-click. Tailwind is precompiled and inlined rather than pulled from a CDN, so the page has no runtime dependency and no flash of unstyled content.

Consequence worth knowing

Because the Tailwind CSS is compiled from this file's own markup at a point in time, a new utility class in fresh markup has no rule behind it and silently does nothing. That is exactly what happened when the Quick access card first went in: lg:col-span-5 did not exist, so the cards stacked instead of sitting side by side. New utilities have to be added to the inlined stylesheet by hand.

What lives outside the file

  • src/i18n/*.json — 13 copy sources, the writable half of the text
  • tools/merge-i18n.js — folds those into the dictionary inside the page
  • tools/checks/*.js — 7 headless browser checks
  • docs/ — audits, research, and design-system notes per feature
Navigation

Routing

One shell — sidebar, top bar, main region — and eleven views that swap inside it. The hash is the whole router. parseHash() splits #/route/id?seg= into three parts and every render reads from there, so any screen is a URL you can paste to a colleague.

An id that is all digits is a record; anything else is a tab name. That one rule lets #/user/2423500 and #/transfers/individual share a parser.

#/overview
Home. Wallet, metrics, chart, quick access, activity, action needed.
#/users
Everyone in the points programme.
#/user/:id
One person: profile, ledger, parked points.
#/followers
An audience, not a subset of Users.
#/follower/:id
Same template as the user detail, different collection.
#/transfers
The approval queue for bulk point transfers.
#/transactions
Every individual movement of points.
#/charges
What the partner paid for their points.
#/exports
Where every Export button on every screen lands.
#/settings
Company profile and the text customers read.
#/releases · /release/:id
App release notes, each shown in both languages.
#/login
Sign in and OTP.

Users and Followers share one view container and one set of render functions. A collection object supplies the differences — headings, column sets, empty-state copy — which is why ck() exists alongside t(): it resolves a key against whichever collection is active.

Bilingual

Copy and language

Every string the reader sees exists twice, in Arabic and English, under one flat dotted key. Writers edit JSON files; the page carries a compiled dictionary. A merge step connects the two.

Six ways a key reaches the DOM

Static markup declares its copy with an attribute, and applyI18n() walks the page applying them: data-i18n for text, plus -aria, -ph (placeholder), -title, -part (half of a two-sentence string), -vars (interpolation), and -coll (resolve against the active collection).

The trap this design carries

Anything built in JavaScript has no data-i18n attribute, so applyI18n() cannot reach it. Every such view has to be redrawn by name inside setLang(), and forgetting one is invisible until somebody switches language.

It has bitten twice: the user profile kept a person's whole ledger in the previous language, and the Overview kept its date filter, activity feed and chart axis. lang-switch.js now switches on every route in both directions and fails if anything is left in the wrong script.

Direction is structural

Arabic is not a translation layer over a left-to-right page. dir flips on the root element and the CSS is written in logical properties throughout — margin-inline-start, inset-inline-end, border-end-start-radius — so the layout mirrors rather than being re-specified. A .ltr helper isolates the things that must not mirror: phone numbers, emails, file names, reference codes.

Design system

The layout system

Two scales, both enforced. Spacing resolves through 17 tokens with 443 references and no loose pixel values left except twelve 1px hairlines. Type is seven sizes — 12, 14, 16, 18, 20, 24, 32 — down from 21, five of which used to be half-pixel values that rendered differently per browser and zoom level.

Colour is tokenised the same way: a primary ramp from the brand's #755BD8, a secondary from #FAC333, a twelve-step neutral, and separate semantic ramps for success, warning, danger and info — kept apart from the accent so a status colour never has to compete with a brand colour.

The interesting part

Tables that fit

Six data tables carry between seven and eleven columns and have to work from a 360px phone to a 1800px monitor. The first version used hand-written width thresholds, which broke at 1101px — the width where the sidebar appears and the container narrows while the window gets wider.

It was replaced by a loop that measures instead of guessing. Draw the table, ask whether it overflows its scroller, drop the least valuable column, draw again. Below three surviving columns it stops fighting and switches to cards.

Because it measures the real rendered table, it is correct at any width in either language without a single breakpoint. Arabic column widths differ from English ones; the loop does not need to know that. column-fit.js proves it across six tables × eleven widths × two languages.

Interaction

Panels

Side panels are a stack, not a boolean. openPanel() pushes, panelBack() pops one step, closePanel() empties it. That is what lets a file open, then a rejection form open on top of it, and Escape step back to the file rather than dumping you at the list.

Focus is trapped inside the open panel and returned to whatever opened it on close. Panels also close with the route that owns them — without that, starting a transfer and then clicking Users left the drawer floating over a screen it had nothing to do with.

Mock data

Data and the rate

Every dataset is generated from a seeded pseudo-random function, so the same 46 users with the same names, phone numbers and balances appear on every load, on every machine. Screenshots stay comparable and a bug found on row 12 is still on row 12 tomorrow.

One rule governs money: 5 points = 1 SAR, everywhere, no exceptions. Value is never stored on a record — it is valueOf(points), computed at render.

const PTS_PER_RIYAL = 5;
const valueOf = pts => pts / PTS_PER_RIYAL;
Why this is a rule and not a helper

Charge history used to build its amounts with points / 500. That single line contradicted the stated rate on every screen it touched and survived four features of review, because each screen looked internally consistent. Deriving value rather than storing it means no record can carry a figure that disagrees with the rate.

Verification

What guards it

Seven headless-browser checks, run against the real rendered page rather than the source. Each one exists because something specific went wrong.

CheckWhat it catches
route-regressionEvery route × both languages: raw keys leaking to screen, views failing to draw, JavaScript errors.
lang-switchAnything left in the language the reader just left — the JS-rendered views applyI18n cannot reach.
arabic-leak-scanLatin text stranded in Arabic copy, across 41 states. Skips blocks that declare the other language on purpose.
column-fitSix tables × eleven widths × two languages: no table may overflow its container.
states-and-keyboardLoading, empty and error states; focus trapping; Escape stepping back through the panel stack.
no-duplicate-namesTwo functions declared with the same name — one silently replaces the other. This happened once and broke the profile tabs with no error.
width-sweepLayout sanity across the full width range.

A check is only kept once it has been shown to fail without the fix it guards. The language-switch check was written after the Overview bug, then verified by removing the fix and confirming it went red — a test that cannot fail is worse than no test.

What comes next

Porting to React

The single file is a prototype for reviewing design decisions, not the shipping codebase. Most of it ports cleanly, and a few things are worth carrying over deliberately:

  • The copy pipeline survives as-is. The JSON sources and the owned-prefix rule are framework-agnostic; only the merge target changes.
  • The redraw problem disappears. React re-renders on a language change by itself, which removes the entire class of bug lang-switch.js exists to catch — though the check is worth keeping pointed at the built app.
  • The fit loop needs a resize observer. It currently runs on render and on window resize; in React it belongs in a hook watching the container, not the window.
  • The panel stack maps to routed modals — the stack is already the right model, so it becomes state rather than an array.
  • Tokens move to CSS custom properties in one stylesheet and stop being duplicated by the inlined Tailwind build.
